# 規則の理由

素の`preset`をそのまま当てると、日本語の技術文書と噛み合わない指摘が出る。
切った規則、ゆるめた規則には、なぜそうしたかを必ず書く。
理由の書けない除外を増やさないためである。

## 前提としている書き方

この設定は、次の書き方を前提にしている。
違う書き方をする場合は、対応する規則を上書きすればよい（README「設定を変える」）。

- 文体は「である調」で統一する。ですます調に切り替えられる
- 一文一行で書く。1行に2文を書かない
- 長い1文を途中で折り返すことは許す
- 表の列幅はエディタが自動でそろえる

## Markdownの規則

`config/markdownlint.jsonc`にある。
既定を土台にし、噛み合わない規則だけを切ってある。

| 規則 | 設定 | 理由 |
| ---- | ---- | ---- |
| MD013 | 切る | 一文一行で書くと、一文が80文字を超えることは普通にある。日本語は文字数と表示幅も一致しないため、行長で測ること自体が噛み合わない |
| MD024 | `siblings_only` | 章ごとに同じ小見出し（「項目」「注意」など）を置く書き方がある。文書の中で一度きりを求めると書けなくなるため、同じ親を持つ見出しどうしだけを見る |
| MD029 | `one` | 順序付きリストはすべて「1.」で書く。順番を入れ替えても差分が1行で済む |
| MD046 | `fenced` | コードブロックはフェンスに統一する |
| MD048 | `backtick` | コードフェンスの記号はバッククォートに統一する |
| MD049 | `asterisk` | 強調の記号はアスタリスクに統一する |
| MD050 | `asterisk` | 太字の記号も同じ |
| MD060 | 切る | 表の記号の揃え方を見る規則である。様式は`aligned`（列幅をそろえる）、`compact`（記号の左右に空白1つ）、`tight`（空白なし）の3つで、既定の`any`はどれでもよいが表の中では統一を求める。列幅をそろえた表に幅の合わない行を1つ足すと指摘されるため、行を足すたびに付け直しを迫られる。日本語は全角と半角が混ざり、エディタによって「そろっている」の意味も変わる |

上に無い規則は既定のままである。
生のHTML（MD033）と裸のURL（MD034）も既定どおり禁じている。

## 日本語の規則

`config/textlint-base.js`にある。
3つの`preset`を土台にし、そこに校正辞書（`prh`）と康煕部首の規則を足している。

### 検査を止めるもの

| 規則 | 設定 | 理由 |
| ---- | ---- | ---- |
| `no-mix-dearu-desumasu` | である調 | `preset`の既定は「ですます」なので入れ替える。ですます調も選べる |
| `sentence-length` | 120文字 | 一文一行で書くと一文が長くなり、既定の100文字では収まらない文がある |
| `ja-no-mixed-period` | 切る | 「最終更新: 2026-09-04」のような、文ではない行を文とみなして指摘する。文末の体裁は`no-mix-dearu-desumasu`が実質的に見ている |
| `4.2.6.ハイフン(-)` | 切る | 「A-B-C」のようなキーや識別子の書式に使う |
| `4.2.7.コロン(：)` | 切る | 「最終更新: 2026-09-04」の形を見出しや前書きで使う |
| `3.3.かっこ類と隣接する文字の間のスペースの有無` | 切る | 下の「箇条書きを壊す規則」を見よ |
| `ja-no-space-around-parentheses` | 切る | 同上 |
| `1.1.1.本文` | 切る | 下の「文体を二重に見る規則」を見よ |
| `1.1.3.箇条書き` | 切る | 同上 |
| `1.1.5.図表のキャプション` | 切る | 同上 |
| `@223n/lint-config-ja/rules/desumasu-ending` | ですます調で入れる | 下の「普通体の文末を拾う規則」を見よ。`desumasuEnding: false`で外せる。である調では入らない |

### 警告として出すもの

直す価値はあるが、検査を止めるほどではないものである。
`textlint`は`error`だけで終了コードを1にするため、警告は検査を通しつつ目に入る。

| 規則 | 見るもの |
| ---- | ---- |
| `no-doubled-joshi` | 助詞の連続 |
| `max-kanji-continuous-len` | 漢字の連続。既定は6文字まで。仕様の用語や固有名詞は言い換えられないことがある |
| `ja-no-redundant-expression` | 冗長な表現 |
| `ja-unnatural-alphabet` | 不自然なアルファベット |
| `prh` | 表記ゆれと誤用。下の「校正辞書」を見よ |
| `no-kangxi-radicals` | 康煕部首。見た目は同じでも別の文字である漢字 |

## 校正辞書

`prh`に読ませている辞書は、VS Code拡張「テキスト校正くん」（`ics.japanese-proofreading`）が
使うものと同じである。`dict/`に同梱した。

`preset`では拾えない種類の指摘である。
`preset`は文の形（長さ、助詞の連続、文体）を見るが、辞書は語そのものを見る。
文の形としては何も問題がない文でも、語を取り違えていることはある。

### 警告にしてある理由

7つの辞書のうち「ひらく漢字」と「外来語カタカナ表記」は、書き手の好みに属する指摘を含む。

<!-- textlint-disable prh -->

- 「出来る」を「できる」に
- 「プリンタ」を「プリンター」に

<!-- textlint-enable prh -->

どちらも誤りではない。これで検査を止めると、既存の文書が一斉に落ちる。
止めたい場合は`proofreadingSeverity: 'error'`を渡す。

### 誤検出もある

辞書は語の対応表であり、文脈を見ない。
たとえば「そのとおりである」の「とおりで」を「道理で」に直そうとする。

その箇所だけ止めるには`textlint-disable`のコメントで囲む。
辞書の側は書き換えない。取得元との差分が分からなくなるためである。

### fixは例文を壊す

`textlint --fix`は辞書の指摘も直す。
誤用そのものを例として載せている箇所に当てると、例の意味が失われる。
この配布物では、`dict/README.md`の対応表を`--fix`が一度そうした。
「アボガド」と書いた側が「アボカド」に直り、どちらも同じ語になった。

例を載せる範囲は、書いた時点で`textlint-disable`で囲んでおく。

## 箇条書きを壊す規則

`3.3.かっこ類と隣接する文字の間のスペースの有無`と`ja-no-space-around-parentheses`を切っているのは、
体裁の好みではなく、`--fix`が文書の構造を壊すためである。

箇条書きの続きの行は、2つのスペースで字下げする。
その行が全角のかっこ（`（`や`」`）で始まると、この2つの規則は字下げをかっこの前のスペースとみなして指摘する。
さらに`--fix`をかけると字下げが削られ、続きの行が別の段落になる。

切っていない場合でも、`--fix`をかけたあとは差分を見るのが安全である。

## 文体を二重に見る規則

`preset-jtf-style`の`1.1.1.本文`、`1.1.3.箇条書き`、`1.1.5.図表のキャプション`を切ってある。
体裁の好みではなく、`no-mix-dearu-desumasu`と正反対を指すためである。

この3つは文体の混在を見る点で`no-mix-dearu-desumasu`と同じだが、**寄せ先を設定できない**。
文書内の多数派に寄せろと指摘する。

そのため`style`を`ですます`にしても、である調が多く残っている文書では
「である調に寄せろ」と言い続ける。
文体を移し替えている最中がまさにその状態であり、そこで矛盾する。

```text
これはテストです。      ← jtf: である調に寄せろ
これは例外である。      ← no-mix: ですます調に寄せろ
これも例外である。      ← no-mix: ですます調に寄せろ
```

どちらに従っても、もう片方が叩き続ける。
文体の判定は、寄せ先を設定できる`no-mix-dearu-desumasu`一本に任せる。

`1.1.2.見出し`（見出しの末尾に句点を付けない）は重ならないので残してある。

## 普通体の文末を拾う規則

`rules/desumasu-ending.js`は、このパッケージが自前で持つ規則である。
`style: 'ですます'`の設定に既定で入る（3.0.0から）。`desumasuEnding: false`を渡すと外れる。

### なぜ足したか

文体の判定を任せている`no-mix-dearu-desumasu`には、2つの穴がある。

- 拾うのは「である」「だ」のような明示的な常体だけである。「〜を確かめる」「〜はない」「〜した」のような普通体の文末は拾わない
- 表のセルは、そもそも見ない

```text
これは例である。          ← no-mix: 指摘する
動作を確かめる。          ← no-mix: 素通りする
| 送信 | 動作を確かめる。 | ← no-mix: 素通りする（表のセル）
```

である調では、普通体の文末は誤りではないので、この穴は問題にならない。
ですます調では、普通体の文末が混ざっても検査を通ってしまう。

### 判定のしかた

文を形態素解析（`kuromojin`）で語に分け、末尾から述語の連なりを集める。
述語の連なりとは、動詞、形容詞、助動詞と、それをつなぐ「て」「で」である。
その中に助動詞の「です」か「ます」があれば、丁寧な文末とみなす。
「ました」「ません」「でした」「でしょう」は「です」「ます」の活用なので、これで通る。
「ください」は動詞なので、命令形のときだけ別に丁寧とみなしている。
「〜てくださる」「〜てくださった」は普通体なので拾う。

述語の後ろの終助詞（「〜ですか」の「か」、「〜ますね」の「ね」）は、外してから述語を見る。
「〜するのか」「〜なのか」の「の」は名詞として解析されるので、これも飛ばして前の述語を見る。
句点で終わる文の末尾の「が」「けど」「から」「ので」のような接続助詞も、外してから見る。
「〜するので」で終わる文は、丁寧にすると「〜しますので」になるためである。

語尾の文字列では判定しない。
「ルール」や「サーバー」は、文字の上では動詞と同じように終わるが名詞である。
文字列で見ると、名詞の一覧を持ち続けることになる。

### 文の区切り

句点（`。`）、疑問符と感嘆符（`？`と`！`）、全角のピリオド（`．`）で文を区切る。
半角の`?`と`!`は、後ろが空白か行末のときだけ区切る。URLの`?q=`で文を割らないためである。

`<br>`と強い改行（行末の空白2つか「\\」）は、断片の区切りにする。
表のセルの「使わない`<br>`推奨」は、表示では2行になるので、2つの断片として見る。
段落の中のただの改行は区切らない。表示では1行につながるためである。

かっこと引用の記号は、段落や表のセルの全体で対を決める。
対になる閉じがある引用の内側は、句点があっても区切らず、文としても見ない。
引用の記号は、かぎかっこ（`「」`、`『』`）、引用符（`“”`、`"`）、`〝〟`、`《》`である。
段落の中の改行をまたいだ引用も、1つの引用として扱う。
閉じ忘れた開きの記号は、記号としてだけ扱う。後ろの文を巻き込まない。

### 報告しないもの

- 名詞、記号、数字、英字で終わるもの。表と箇条書きには体言止めが多く、これを拾うと指摘が使えなくなる
- 閉じかぎや閉じの引用符で終わるもの。「〜する」と書いた引用で終わる文が多い
- 文を言い切らない形（連用形など）で終わるもの。表の「あり」「なし」「済み」は、形の上では動詞や形容詞だが、名詞として置かれている。「簡単な」「〜のような」も、名詞にかかる形なので報告しない
- 表の見出しの行。「何に使うか」「どうするか」のような列の名前は文ではない
- 断片の「〜か」（「WebPを書き出せるか」）。箇条書きや表に名詞のように置いた問いである。「書き出せますか」に直すと、直接の問いになり意味が変わる。句点や疑問符で終わる「〜するか」は報告する
- 接続助詞で終わる断片（「保存すると」「保存するので」）。表の左の列に条件を置く書き方で、言い切っていない。「〜すると」を丁寧にした「〜しますと」は不自然でもある。句点で終わる文でも、「〜と」「〜ば」「〜て」で終わるものは報告しない
- 断片の「〜せず」。連用形と同じく、言い切っていない形として扱う。句点で終わる「〜せず」は報告する
- ページ内リンク（`#…`）の文字列。目次のように、見出しを写したものが多い。見出しは見ないので、写したものも見ない
- URLを書いた文字列（`<…>`と裸のURL）と、画像の代替テキスト。どちらも書き手の文ではない。裸のURLの後ろに空白を置かずに続けた文は、Markdownの解析ではURLに入るが、文として見る
- リンクだけを並べた箇条書きの項目と表のセル（句点で終わらないもの）。リンクの文字列はページの名前である

文末の注記は外してから判定する。
かっこの注記（「（4.10）」「【未確認】」「［1］」「〔注〕」）、参照の印（「※1」）、`<sup>`の注の番号、コロン、絵文字である。
述語の後ろに付いても、文末の形は変わらないためである。
かっこの中に句点で終わる文があれば、それも書き手の文として見る。
表のセルや箇条書きの項目の全体がかっこの中にあるとき（「（後で決める）」）は、その内側を見る。

### 断片も見る理由

表のセルと箇条書きの項目は、句点を付けずに書くことが多い。
「派生画像はブラウザで作る」「使わない」のような断片を見なければ、表の中の普通体はほとんど拾えない。

本文の段落では、句点で終わる文だけを見る。
「最終更新: 2026-09-04」のような、文ではない行を拾わないためである。

断片を見ると、表の値として並べた「行う」「行わない」も拾う。
表に置いた人名（「わたる」「ひかる」）やラベル名（「対応しない」）も、形態素解析では動詞になるので拾う。
形の上では文の普通体と区別できない。
そうした文書では、`checkFragments: false`にするか、`allow`に足すか、その範囲をコメントで止める。

### 拾えないもの

次のものは、分かっていて拾わない。

- 「〜できるはず」「〜するつもり」のように、形式名詞で終わる文。名詞で終わるので、体言止めと同じに通る
- 段落の中のただの改行で折り返した箇条書きの、途中の行の末尾。表示では1行につながるので、最後の行の末尾だけを見る

### 既定で入れる理由

ですます調を選んだ文書に普通体の文末が混ざるのは、選んだ文体に反している。
それを検査が素通りさせると、ですます調の設定を選んだ意味が薄れる。

一方で、指摘は多くなりやすい。
ですます調で書いた文書に当てても、表の値として並べた「行う」「行わない」や、
条件を並べた箇条書きの「〜を指定した」が拾われる。
そのため、既定で入れる変更は互換性のない変更として、3.0.0で出した。
すぐに直せない利用側は、`desumasuEnding: false`で外してから、少しずつ直せばよい。

### fixは付けない

「確かめる」を「確かめます」に、「ない」を「ありません」に直すには、活用の種類と文脈が要る。
直し方を誤ると、意味の変わった文が黙って残る。
そのため指摘だけを出し、直すのは書き手に任せる。

### no-mix-dearu-desumasuと重なる

「〜である」「〜だ」で終わる文は、`no-mix-dearu-desumasu`とこの規則の両方が指摘する。
同じ文に2つの指摘が出るが、片方を切っても、もう片方が拾う。

## 意外と引っかかる規則

全角と半角の間にスペースを入れないことを求める規則は、既定で有効にしてある。

```text
正規表現は JavaScript のものである。   ← 指摘される
正規表現はJavaScriptのものである。     ← 通る
```

半角の語をコードスパンに入れれば、この規則からは外れる。
ただし、コードスパンの前後にスペースを入れると別の規則が指摘する（下の「コードスパン・リンク・スラッシュの前後」）。

```text
規則は`markdownlint-cli2`が読む。      ← 通る
規則は `markdownlint-cli2` が読む。    ← 別の規則が指摘する
```

表の中も指摘されない。
半角の語が多い文は、コードスパンに入れるか表に置くと読みやすさを保てる。

この規則は2つある。
`preset-ja-spacing`の`ja-space-between-half-and-full-width`と、
`preset-jtf-style`の`3.1.1.全角文字と半角文字の間`である。
片方だけを切っても、もう片方が同じ指摘を出す。

`halfWidthSpacing`はこの2つをまとめて扱う。

| 設定 | `これは JavaScript の文` | `これはJavaScriptの文` |
| ---- | ---- | ---- |
| `'never'`（既定） | 指摘される | 通る |
| `'always'` | 通る | 指摘される |
| `false` | 通る | 通る |

### コードスパン・リンク・スラッシュの前後

コードスパン、リンク、スラッシュの前後にもスペースを入れない。
`preset-ja-spacing`のv3の既定どおりである。

```text
規則は `markdownlint-cli2` が読む。    ← 指摘される
詳しくは [README](README.md) を見る。  ← 指摘される
型はstruct / enumから選ぶ。            ← 指摘される
値は1 / 2である。                      ← 指摘される
```

コードスパンとリンクで見るのは、日本語の文字と接する側だけである。
`` `i` `m` `s` `u` ``のように、コードスパンどうしを空白で区切って並べるのは通る。
こちらは表の中でも指摘される。

スラッシュは、前後の文字を問わず、スペースがあれば指摘される。
ただし表の中は見ない。

`halfWidthSpacing`を`'always'`にしても、この3つは変わらない。
変えたい場合は、READMEの「規則を個別に上書きする」の手順で上書きする。

強調と斜体の前後は見ない。
こちらもv3の既定どおりである。

## 同じことを見る規則が複数ある

`preset-jtf-style`と`preset-ja-spacing`には、似たことを見る規則が両方にある。

| 見るもの | `preset-jtf-style` | `preset-ja-spacing` |
| ---- | ---- | ---- |
| 全角と半角の間のスペース | `3.1.1.全角文字と半角文字の間` | `ja-space-between-half-and-full-width` |
| 全角どうしの間のスペース | `3.1.2.全角文字どうし` | `ja-no-space-between-full-width` |
| カタカナ語の間のスペース | `3.2.カタカナ語間のスペースの有無` | `ja-nakaguro-or-halfwidth-space-between-katakana` |
| かっこの前後のスペース | `3.3.かっこ類と隣接する文字の間のスペースの有無` | `ja-no-space-around-parentheses` |

同じ箇所に二重の指摘が出ることは、確かめた範囲では無かった。
ただし片方を切っても、指摘が消えないことはある。
規則名がどちらの`preset`のものかを見て、そちらを切る。

全角と半角の間だけは`halfWidthSpacing`が両方をまとめて扱う。
かっこの前後は既定で両方とも切ってある。

## 規則を上書きする

利用側で個別に変えられる。
書き方はREADMEの「設定を変える」にある。

上書きするときは、なぜ変えたかをその場に書くとよい。
理由の書けない除外が増えると、規則そのものが形骸化する。
