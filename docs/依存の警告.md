# 依存の警告について

供給経路を見る道具（Socketなど）にこのパッケージをかけると、依存の木に対する警告が並ぶ。
「難読化コード」のような、強い文言のものも並ぶ。

この文書は、その警告を1つずつ実地に確かめた結果である。
**結論から言えば、対応を要する危険は見つからなかった。**

## まず区別すること

供給経路の道具は、2つの別々のものを見せる。

| 見ているもの | 中身 |
| ---- | ---- |
| パッケージの警告 | このパッケージ自身のコード。8ファイル |
| **依存の警告** | 依存の木**全体**。295パッケージ |

強い文言が並ぶのは後者である。
このパッケージが直接依存しているのは4つだけで、そこから`textlint`の生態系が広がる。

```text
@223n/lint-config-ja
├── textlint-filter-rule-comments
├── textlint-rule-preset-ja-spacing
├── textlint-rule-preset-ja-technical-writing
└── textlint-rule-preset-jtf-style
```

## このパッケージ自身

npmに上げている中身は8ファイルである。

```text
config/textlint.js  config/textlint-base.js  config/textlint-desumasu.js
config/markdownlint.jsonc
bin/lint-vocabulary.mjs
package.json  README.md  LICENSE
```

この中に`eval`と`new Function`は無い。
`child_process`による起動も、外部への通信も無い。
環境変数を読む箇所も無い。
インストール時に走るスクリプトは持たない。

## 依存の木を実測した結果

危険かどうかは、警告の語ではなく**到達経路**で決まる。
295パッケージすべてを走査して確かめた。

| 見たもの | 結果 |
| ---- | ---- |
| 依存の総数 | 295 |
| インストール時に走るスクリプト | **0** |
| レジストリ以外を出所とする依存 | **0** |
| 完全性の検証値（`integrity`）が無いもの | **0** |
| 外部通信を読み込むファイル | **0** |
| シェルを起動するファイル | 1（到達しない。後述） |
| 既知の脆弱性（`npm audit`） | **0** |
| コピーレフトのライセンス | **0** |

ライセンスの内訳は次のとおりで、すべて許容的である。

| ライセンス | 数 |
| ---- | ---- |
| MIT | 285 |
| BSD-2-Clause | 3 |
| ISC | 3 |
| Apache-2.0 | 2 |
| BSD-3-Clause | 2 |

開発時の依存として使うときの実害は、次の2つに限られる。

1. インストールした瞬間に走るもの
1. 検査を走らせたときに動くもの

**どちらも成立しない。**
1つ目はスクリプトが1件も無い。
2つ目は、外部通信とシェル起動のどちらも到達しない。

## 強い警告の正体

### 難読化コード

該当したファイルはすべて、縮小して配る成果物だった。
`Closure Compiler`、`browserify`、`microbundle`のいずれかの出力である。

決め手は、いちばん重いとされた`zlibjs`の末尾にある文字列である。
これは隠された中身ではなく、**元のソースを丸ごと含むソースマップ**だった。
復号すると著作権表示ごと元のコードが出てくる。
意図を隠す目的なら、原本を同梱しない。

しかもその`zlibjs`は、Nodeでは1バイトも読み込まれない。

```text
kuromoji を読み込んだあとの読み込み済み一覧
  zlibjs                   0 件
  BrowserDictionaryLoader  0 件   ← eval を含むのはこちら
  NodeDictionaryLoader     1 件   ← 実際に使われるのはこちら
```

`zlibjs`を読むのはブラウザ向けの読み込み器だけで、Nodeからは選ばれない。

### 差し替え版が利用できる

道具の提供元が、自社で作り直したパッケージへの差し替えを勧めるものである。
元のパッケージに欠陥があるという指摘ではない。

**採用していない。**
検査のための開発時の依存のために、新しい発行元への信頼を増やす見返りが無いためである。

## そのほかの警告

| 警告 | 実際のところ |
| ---- | ---- |
| `eval`を使う | 渡しているのは固定の文字列である。実データが入る口は後述の1件だけ |
| シェルへのアクセス | 1ファイルのみ。公開物に紛れ込んだ開発用スクリプトで、どこからも読み込まれない |
| ネットワークへのアクセス | ブラウザ向けの分岐である。Nodeでは選ばれない |
| 名前の偽装の疑い | 向きが逆である。指摘された`regx`は2016年公開で、似ているとされた側より8年早い |
| 保守されていない | 実体は「本当に放置」と「版が古いだけ」の混在である。後者は上流の更新を待つもの |
| 許容的でないライセンス | 独自の文言を持つ`NOTICE`と、古い書式の記載を拾ったものである。実質はどちらも許容的 |
| 環境変数へのアクセス | 読むのは`DEBUG`や`COLUMNS`など、動作の切り替えに使うものだけである |
| ファイルへのアクセス | 書き込む部分は、親が読み込んでいないため動かない |
| 埋め込まれたURL | 仕様書と文書への参照である。送信先は1つも無い |

## 唯一の注意点

`prh`という規則が、`js-yaml`の古い版で設定を読む。
この組み合わせでは、`!!js/function`と書かれたYAMLを読ませるとコードが動く。

**いまの使い方では発火しない。**
`prh`に渡るのはパッケージに焼き込まれた文字列だけで、外部のファイルを読む設定にはなっていない。
検査対象の文書をどう書いても、この経路には届かない。

効いてくるのは、**第三者が配布する`prh`の規則ファイルを自分で読み込む設定にした場合**である。
そのときは、読ませるファイルの出所を自分が管理するものに限ること。

## 自分で確かめる

同じことを手元で確かめられる。

```bash
mkdir /tmp/deptree && cd /tmp/deptree
npm init -y >/dev/null
npm install @223n/lint-config-ja
```

インストール時に走るスクリプトの有無を見る。

```bash
node -e '
  const l = require("./package-lock.json")
  const e = Object.entries(l.packages).filter(([k]) => k.startsWith("node_modules/"))
  console.log("総数:", e.length)
  console.log("インストール時のスクリプト:", e.filter(([, v]) => v.hasInstallScript).length)
  console.log("レジストリ以外:", e.filter(([, v]) => v.resolved && !v.resolved.startsWith("https://registry.npmjs.org/")).length)
'
```

外部通信とシェル起動を探す。

```bash
grep -rlE "require\(['\"](https?|net|tls|dgram|http2)['\"]\)" node_modules --include='*.js' | wc -l
grep -rlE "require\(['\"]child_process['\"]\)" node_modules --include='*.js'
```

既知の脆弱性を見る。

```bash
npm audit
```

## この文書の前提

`@223n/lint-config-ja@1.0.0`の依存の木を、2026年9月に確かめた結果である。

依存の版が上がれば結果は変わりうる。
版を上げたときは、上の手順をもう一度なぞるとよい。

供給経路の道具が出す警告は、語の一致で拾われることが多い。
**語があるかではなく、そこへ実際に届くかを見ること。**
